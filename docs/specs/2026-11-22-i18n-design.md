# Interface languages (pt-BR, es, en) — design

Date: 2026-11-22 · Domain: frontend · Risk: medium (touches most files; no data, auth or contract change)

## Problem

Every user-facing string of Video Studio is Portuguese, written inline in components, label maps and
form models (about 180 files in `apps/web/src` and `packages/ui/src`). The owner wants the whole
interface in pt-BR (default, text unchanged), es and en, with a switch in the top bar.

## Chosen approach: a small typed in-house dictionary

- **Locale module** in `packages/ui/src/i18n/` (same place and style as `theme.ts`): `Locale =
  'pt-BR' | 'es' | 'en'`, `LOCALE_COOKIE_NAME = 'vs-locale'`, `parseLocale(value)` (allowlist, else
  `undefined`), `negotiateLocale(acceptLanguage)` (allowlist; `pt*` to pt-BR, `es*` to es, `en*` to
  en, by q-weight order, else pt-BR) and `resolveLocale(cookie, acceptLanguage)`: cookie, then
  header, then pt-BR.
- **Catalogues.** `pt-BR` is the source of truth: a nested `as const` object whose shape defines
  `Messages`. `es` and `en` are typed `Messages`, so a missing or extra key fails `typecheck`.
  Parameterised texts are functions (`(count: number) => string`), so parameters are typed; plurals
  use `Intl.PluralRules(locale)` inside the function. No ICU strings, no runtime parser.
  The UI package owns `UiMessages` (its components' texts); the web app owns `WebMessages` (one
  sub-object per feature folder); both are catalogued per locale in `messages/<locale>.ts`.
- **Reading messages.**
  - Server components: `await getI18n()` (`apps/web/src/lib/i18n/server.ts`, `server-only`) reads the
    `vs-locale` cookie and `Accept-Language` and returns `{ locale, t }`.
  - Client components: the root layout renders `<I18nProvider locale messages>` (client context); client
    components call `useI18n()`. Only the messages of the chosen locale are sent. Provider messages
    carry only the locale id (functions do not cross the server/client boundary). **Parameterised
    texts (decided in ticket 01):** the three catalogues ship in the client bundle and
    `useI18n()` / `useWebMessages()` index them by locale, so function-valued texts work unchanged on
    both sides. Cost: a few KB of text per extra language, acceptable for one local owner.
  - `packages/ui` components never import a catalogue; they take their texts from props or
    `useI18n()`, so the kit stays reusable.
- **Switch.** `LanguageSwitch` (ui, client) is a three-option `radiogroup` styled like `ThemeToggle`,
  placed next to it in the studio shell and on `/login`. Choosing writes `vs-locale` (Path=/,
  one year, SameSite=Lax), same as the theme cookie, then `router.refresh()` so server-rendered
  text, `<html lang>` and metadata change without a full reload. No inline script, so the nonce-based
  CSP is untouched.
- **`<html lang>`** is the resolved locale. Titles: `metadata` becomes `generateMetadata()` per page
  using `getI18n()`; the template suffix (`EngineOS Video Creator`) stays the product name.
- **Dates and numbers** go through `Intl` with the active locale: `packages/ui/src/utils/format.ts`
  takes a `locale` argument (default pt-BR keeps today's output byte for byte); a `formatDate`,
  `formatDateTime`, `formatRelative` set replaces ad-hoc `toLocale*` calls. Currency stays USD.
- **Routes** keep their pt-BR paths (`/execucoes`, `/catalogo`): a language is not part of the URL.
- **API error texts.** The api's own `message` stays English and is never shown; the reason-keyed
  maps in `features/common/api-error-text.ts` become catalogue entries. `Record<ApiRev5ErrorReason,
  ...>` typing is kept per locale, so a new reason without a text in any language fails the build.
- **Brand.** User-facing text calls the product "Spesia" where the owner asked for it; the existing
  `EngineOS Video Creator` product name in titles is not renamed by this feature (see Open points).

## Rejected alternatives

- **`next-intl`.** Mature and typed with extra setup, but it adds a runtime dependency, wants its own
  request config and (for locale routing) middleware that would have to share the CSP middleware,
  and its ICU messages are untyped unless a global type augmentation is added. Three languages, one
  owner, no locale in the URL, no translators' tooling: the small dictionary gives the same type
  safety with no dependency. Reconsider if a fourth language or translator workflow appears.
- **Locale in the URL (`/es/execucoes`).** Rejected: every route, redirect and BFF path would change,
  and it duplicates what a cookie already does for one local owner.
- **One flat key-string catalogue (`t('runs.status.running')`).** Rejected: stringly keys defeat the
  typecheck guarantee unless a key-path type is derived; plain nested object access (`t.runs.status.running`)
  gets autocompletion and missing-key errors for free.

## Boundaries and ordering

- `login/page.tsx`, `features/auth/*` and the dev-only auto sign-in route are owned by another session;
  they are translated in the **last** ticket, after the owner says that work landed.
- `packages/ui/src/styles/tokens.css` is never touched.
- Today's pt-BR text stays exactly as is: the pt-BR catalogue is a move of the current strings, and a
  ticket's review compares them.

## Testing

Lint and typecheck run once at the end after explicit approval. Tests and builds only on explicit
approval. Unit tests written by the final-gate ticket: `parseLocale`, `negotiateLocale`,
`resolveLocale`, and a catalogue test that pt-BR, es and en have identical key paths and the same
parameter arity.

## Non-goals

Translating the api's English `message`, the CLI (`tools/cli`), `packages/shared` contract data,
generated run files, user-entered content, or route paths. Right-to-left languages.

## Open points

1. `packages/shared` holds some pt-BR strings (zod messages, platform labels). Ticket 03 lists those
   that reach the screen; they are moved behind the catalogue where the web shows them.
2. Brand wording ("Spesia" versus the current "EngineOS Video Creator" in titles and logo labels) is
   confirmed by the owner before ticket 10.

## Revision 2026-11-23: entire system

- Scope widened: every page body of `apps/web`, the `@studio/ui` defaults and the `apps/shell` menu
  follow the active language; `tools/cli` follows the system locale (its own catalogue). The CLI is no
  longer a non-goal.
- Glossary and translation rules: `design/glossario.md`.
- Plurals: `count === 1 ? singular : plural` inside the catalogues, in all three languages.
  `Intl.PluralRules` is not used (it treats 0 as singular in pt).
- Formatters take the locale as a required parameter (`@studio/ui` `formatUsd`, `formatBytes`,
  `formatNumber`, `formatDate`, `formatDateTime`, `formatRelative`; web `lib/i18n/format.ts`), so a
  forgotten locale fails typecheck. 24-hour clock in every locale.
- New web catalogue groups: `publishing`, `platforms`, `auth`; `recipes`, `schedules`, `curations`
  (with comparisons) and `metrics` (with insights) are filled.
- Watcher run files are not changed. pt-BR shows the recorded owner text; es and en rebuild event
  lines and waiting notices from their structured fields and keep unstructured recorded prose as is,
  marked `lang="pt-BR"`. A `textKey` plus params in a future RUN-FORMAT version is the follow-up.
- The api already sends stable `reason` codes; the web owns their texts. The shared pt-BR display
  constants (`apiRev7ErrorTexts`, `capabilityStatusLabels`) stay unchanged and the web no longer
  displays them directly.
